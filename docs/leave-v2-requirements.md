# 2차 휴가 고도화 요구사항

## 1. 2차 개발 목표

2차 휴가 고도화의 목표는 1차 MVP의 휴가 요청/승인 안정성을 유지하면서, 휴가를 연차와 맞춤휴가로 분리하고 정책 기반으로 운영할 수 있게 만드는 것이다.

핵심 목표:

- 관리자가 맞춤휴가 유형을 만들 수 있다.
- 관리자가 직원에게 맞춤휴가를 지급할 수 있다.
- 휴가 잔여 변화가 장부처럼 추적된다.
- 휴가 요청 단위가 날짜별로 확장 가능해진다.
- 증명자료 정책을 유형별로 관리한다.
- 향후 승인 정책 확장 기반을 만든다.

## 2. 2차 개발 범위

- 휴가 유형 모델 정리
- 맞춤휴가 정책 관리
- 맞춤휴가 지급
- LeaveLedger 기반 잔여 추적
- LeaveRequestSegment 기반 요청 단위 확장
- 증명자료 metadata 정책
- 휴가 사용 내역/히스토리 조회
- 기본 승인 정책 모델 초안

## 3. 2차에서 제외할 범위

- 실제 파일 스토리지 연동
- 실제 이메일/알림 연동
- 연차 촉진 자동화
- 퇴직자 정산
- 연차수당 계산
- 복잡한 순차 승인 전체 구현
- 외부 캘린더 연동
- 급여/근태 시스템 연동

## 4. 사용자 역할별 요구사항

| 역할 | 요구사항 |
| --- | --- |
| OWNER | 모든 휴가 유형, 정책, 지급, 장부, 승인 정책을 관리한다. |
| LEAD | 담당 팀 휴가 요청을 확인하고 승인/반려/취소한다. 2차에서는 맞춤휴가 정책 관리는 하지 않는다. |
| MANAGER | 자기 휴가 잔여와 지급 내역을 확인하고 휴가를 요청한다. |
| EXTERNAL_PARTNER | 2차 휴가 기능 접근 대상이 아니다. |

## 5. OWNER 요구사항

- 연차 정책과 맞춤휴가 정책을 구분해서 볼 수 있다.
- 맞춤휴가 유형을 생성/수정/비활성화할 수 있다.
- 맞춤휴가별 유급/무급, 부여 방식, 사용 단위, 증빙 정책을 설정할 수 있다.
- 직원에게 맞춤휴가를 지급할 수 있다.
- 직원별 휴가 장부를 조회할 수 있다.
- 휴가 정책 변경과 지급 이력을 AuditLog에서 확인할 수 있다.

## 6. LEAD 요구사항

- 담당 팀 및 하위 팀 직원의 휴가 요청을 확인한다.
- 승인/반려/취소 권한은 1차 MVP 원칙을 유지한다.
- 자기 자신의 휴가 요청은 직접 처리할 수 없다.
- 맞춤휴가 정책이나 지급은 관리하지 않는다.

## 7. MANAGER 요구사항

- 자신에게 지급된 연차와 맞춤휴가 잔여를 구분해서 볼 수 있다.
- 맞춤휴가별 사용 조건과 증빙 안내를 확인할 수 있다.
- 휴가 요청 시 사용 가능한 단위만 선택할 수 있다.
- 요청 상태와 장부 반영 내역을 확인할 수 있다.

## 8. 휴가 유형 관리 요구사항

관리자는 다음 항목을 설정할 수 있어야 한다.

- 휴가명
- 설명
- 연차/맞춤휴가 구분
- 유급/무급 여부
- 유급 비율
- 사용 가능 단위
- 증명자료 정책
- 휴일 포함 차감 여부
- 공개 범위
- 비활성화 여부

1차 MVP의 `LeaveType` enum은 바로 제거하지 않는다. 2차 migration 계획에서 기존 enum 값을 신규 휴가 유형 데이터로 매핑한다.

## 9. 맞춤휴가 지급 요구사항

- OWNER는 특정 직원에게 맞춤휴가를 지급할 수 있다.
- 지급 수량과 만료일을 입력할 수 있다.
- 지급 사유를 입력해야 한다.
- 지급은 LeaveLedger에 `GRANTED` 이벤트로 남는다.
- 지급 취소 또는 조정은 별도 이벤트로 남겨야 하며 hard delete하지 않는다.

## 10. 휴가 요청 화면 요구사항

- 직원은 휴가 유형을 먼저 선택한다.
- 선택한 휴가 유형에 따라 사용 가능 단위, 증빙 필요 여부, 잔여 수량을 확인한다.
- 여러 날짜를 하나의 요청으로 묶을 수 있다.
- 날짜별로 하루종일/오전 반차/오후 반차/시간 단위/분 단위를 표현할 수 있어야 한다.
- 2차 초반에는 시간/분 단위 UI를 바로 열지 않고 데이터 모델만 준비할 수 있다.

## 11. 휴가 잔여 계산 요구사항

- 잔여 계산은 단일 helper 또는 service를 source of truth로 유지한다.
- 연차와 맞춤휴가 잔여를 구분한다.
- PENDING, APPROVED, REJECTED, CANCELLED, WITHDRAWN 상태 반영 원칙을 유지한다.
- 장부 이벤트와 요청 상태가 불일치하지 않도록 transaction 경계를 명확히 한다.

## 12. 휴가 장부 요구사항

LeaveLedger는 다음 이벤트를 기록한다.

- `GRANTED`
- `USED`
- `PENDING`
- `PENDING_RELEASED`
- `EXPIRED`
- `ADJUSTED`
- `CANCELLED`
- `REJECTED`
- `WITHDRAWN`
- `CARRIED_OVER`

장부에는 다음 정보가 필요하다.

- 대상 사용자
- 휴가 유형
- 기준 연도 또는 유효기간
- 수량
- 이벤트 유형
- 연결된 휴가 요청
- 연결된 지급/조정
- 생성자
- 사유
- 생성일

## 13. 증명자료 요구사항

증명자료 정책은 다음 값을 지원한다.

- 불필요
- 요청 전 필수
- 요청 후 제출 가능
- 선택 제출

2차 초반에는 `attachmentUrl` 또는 metadata로 시작한다. 실제 파일 저장소, 권한별 파일 다운로드, 만료 URL은 후속 단계로 둔다.

## 14. 승인 정책 요구사항

2차에서는 승인 정책 모델을 설계하되, 복잡한 순차 승인 전체 구현은 후순위로 둔다.

후보:

- 승인 불필요
- 단일 승인
- OWNER 승인
- 팀 리드 승인
- 지정 승인자 승인
- 순차 승인

1차의 OWNER/LEAD 승인 원칙은 기본값으로 유지한다.

## 15. 감사 로그 요구사항

다음 이벤트는 AuditLog에 남긴다.

- 휴가 유형 생성/수정/비활성화
- 맞춤휴가 지급/조정/취소
- 장부 이벤트 생성
- 증명자료 제출/수정
- 승인 정책 변경
- 연차 정책 변경

민감한 증명자료 내용, 파일 URL, 개인정보는 과도하게 metadata에 저장하지 않는다.

## 16. 테스트 요구사항

필수 테스트:

- 기존 1차 휴가 요청/승인 회귀 테스트
- 맞춤휴가 생성/수정/비활성화
- 맞춤휴가 지급
- 지급 후 잔여 계산
- 장부 이벤트 생성
- PENDING/APPROVED/CANCELLED/WITHDRAWN 상태별 장부 정합성
- 증빙 필수 정책 검증
- LEAD 담당 범위 승인 제한
- OWNER 정책 관리 권한
- MANAGER 정책 관리 차단

## 17. 2차 1단계 구현 상태: 휴가 유형 관리

2차 1단계에서는 휴가 유형 관리 기반을 구현한다.

구현 범위:

- OWNER 전용 휴가 유형 목록 조회
- 휴가 유형 생성
- 휴가 유형 수정
- 휴가 유형 비활성화/재활성화
- 시스템 기본 휴가 보호
- 휴가 유형별 정책 필드 저장
- 휴가 유형 변경 AuditLog 기록

시스템 기본 휴가:

- 연차
- 반차
- 예비군
- 병가
- 경조사

관리자 생성 휴가는 회사가 자체적으로 운영하는 맞춤휴가다. 2차 1단계에서는 유형과 정책을 만들 수 있고, 직원에게 직접 지급하는 기능은 다음 단계에서 구현한다.

2차 1단계에서 제외되는 범위:

- 맞춤휴가 직원 지급
- LeaveGrant
- LeaveLedger 실제 도입
- LeaveRequestSegment
- 시간/분 단위 요청
- 파일 업로드
- 연차 정책 고도화
- 순차 승인 정책

## 18. 2차 2단계 구현 상태: 맞춤휴가 지급

2차 2단계에서는 OWNER가 직원에게 맞춤휴가를 지급하고, 지급 내역을 조회하거나 회수할 수 있는 기능을 구현했다.

포함 범위:

- OWNER 전용 맞춤휴가 지급 화면
- 단일 직원 지급
- 여러 직원 일괄 지급
- 지급 내역 목록 및 상세 조회
- 사용 또는 승인 대기 수량이 없는 지급 내역 회수
- 직원 내 휴가 화면의 맞춤휴가 보유 카드
- 직원별 휴가 보유 현황의 맞춤휴가 현황 섹션
- `LEAVE_GRANT_CREATED`, `LEAVE_GRANT_BULK_CREATED`, `LEAVE_GRANT_REVOKED` AuditLog

정책 원칙:

- 연차 추가/차감은 `LeaveAdjustment`로 처리한다.
- 맞춤휴가는 `LeaveGrant`로 지급한다.
- 지급 가능한 휴가 유형은 `category = CUSTOM`, `isEnabled = true`, 직접 지급 가능한 `grantMethod`를 가진 휴가 유형이다.
- 같은 직원에게 같은 맞춤휴가를 여러 번 지급할 수 있다.
- 이번 단계에서는 지급받은 맞춤휴가를 휴가 요청에 사용하는 흐름을 구현하지 않는다.

2차 2단계 제외 범위:

- 맞춤휴가 요청 생성
- 맞춤휴가 승인/반려/취소와 `LeaveGrant` 잔여 연결
- `LeaveRequestSegment`
- 시간/분 단위 휴가 요청
- `LeaveLedger` 전면 도입
- 파일 업로드

## 19. 생일 반차 자동 지급

생일 반차는 직원 생일 기준으로 매년 자동 지급되는 맞춤휴가입니다.

정책:

- 휴가 유형 code: `BIRTHDAY_HALF_DAY`
- category: `CUSTOM`
- 연차 차감 없음
- 지급 수량: 0.5일
- 지급 단위: DAY
- 사용 단위: HALF_DAY
- 사용 가능 기간: 생일부터 7일 뒤 날짜까지 포함
- 지급일: 생일 하루 전
- 지급일이 토요일/일요일/회사 휴일이면 직전 영업일로 이동
- 2월 29일 생일은 평년 2월 28일 처리

구현 범위:

- `BirthdayLeavePolicy`로 자동 지급 사용 여부와 기간 설정
- 매일 실행 가능한 `jobs:birthday-half-day-grants` script
- `LeaveGrant.source = BIRTHDAY_AUTO`
- `referenceYear`, `referenceDate`를 통한 중복 지급 방지
- 지급 성공 시 인앱 `Notification` 생성
- OWNER 정책 설정 화면
- 직원 알림 목록

이번 단계 제외:

- 생일 반차를 실제 휴가 요청에 연결
- 이메일/Slack/카카오톡 알림
- 2월 29일 처리 방식 선택 설정
- 수동 재지급 워크플로우
# 최근 구현: 휴가 증명자료 제출/검수

- 휴가 유형별 `attachmentPolicy`를 실제 요청 생성 흐름에 반영한다.
- `REQUIRED_BEFORE_REQUEST`는 요청 생성 시 파일 제출을 요구한다.
- `REQUIRED_AFTER_REQUEST`는 요청 생성 후 제출 필요 상태로 관리한다.
- 직원은 자기 휴가 요청 상세에서 증명자료를 추가 제출할 수 있다.
- OWNER와 담당 LEAD는 승인 상세에서 증명자료를 다운로드하고 확인 완료, 반려, 재제출 요청을 처리한다.
- 첨부파일은 private storage에 저장하며 public 경로와 fileKey 직접 접근을 허용하지 않는다.
- 실제 외부 스토리지, 바이러스 검사, OCR은 후순위다.
## 2차 8단계: 휴가 승인 정책

- OWNER는 휴가 유형별 승인 정책을 생성, 수정, 비활성화할 수 있다.
- 휴가 유형은 하나의 승인 정책을 참조할 수 있다.
- 승인 방식은 자동 승인(`NONE`)과 단일 승인(`SINGLE`)을 우선 지원한다.
- 승인자 규칙은 `OWNER`, `TEAM_LEAD`, `TEAM_LEAD_OR_OWNER`, `CUSTOM_USER`를 지원한다.

## 2차 9단계: 휴가 캘린더와 공개 범위

- 공통 내부 사용자는 `/leaves/calendar`에서 권한에 맞는 휴가 일정을 확인한다.
- OWNER는 전체 직원의 `APPROVED`/`PENDING` 휴가를 볼 수 있다.
- LEAD는 담당 팀 및 하위 팀 직원의 `APPROVED`/`PENDING` 휴가를 볼 수 있다.
- MANAGER는 자기 휴가와 같은 팀 구성원의 공개 가능한 `APPROVED` 휴가만 볼 수 있다.
- `PUBLIC_WITH_TYPE` 휴가는 휴가 유형까지 표시한다.
- `PUBLIC_AS_LEAVE` 휴가는 일반 구성원에게 `휴가`로만 표시한다.
- `PRIVATE_TO_APPROVERS` 휴가는 권한 없는 일반 구성원에게 표시하지 않는다.
- 캘린더 DTO에는 휴가 사유, 증명자료, 첨부파일, 검토 코멘트를 포함하지 않는다.
- 외부 캘린더 연동은 3차 이후로 둔다.
- 순차 승인(`SEQUENTIAL`)은 데이터 구조와 문서상 확장 포인트로만 둔다.
- 반려 사유와 승인 취소 사유의 필수 여부는 정책별로 설정할 수 있다.
- 요청자 본인은 어떤 정책에서도 자기 휴가를 직접 승인할 수 없다.
