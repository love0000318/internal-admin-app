# 백업 및 복구 가이드

## 1. DB 백업이 필요한 이유

DB에는 사용자, 초대, 조직, 휴가 요청, 휴가 잔여 계산에 필요한 기록, AuditLog가 저장됩니다. DB 손실은 실제 운영 기록 손실로 이어집니다.

## 2. 배포 전 백업

앱 배포 전 운영 DB 백업을 수행합니다. 특히 migration이 포함된 배포라면 백업 없이는 진행하지 않습니다.

## 3. Migration 전 백업

Prisma migration 적용 전 백업을 수행합니다. migration 실패 시 복구 기준점이 됩니다.

## 4. 정기 백업 권장 주기

- 운영 DB: 최소 1일 1회 자동 백업
- 중요 배포 전: 수동 백업
- 대량 직원/휴가 데이터 수정 전: 수동 백업

## 5. 백업 파일 보관 주의

- 백업 파일에는 개인정보가 포함될 수 있습니다.
- 접근 권한을 제한합니다.
- 외부 공유 저장소에 평문으로 업로드하지 않습니다.

## 6. 복구 전 확인 사항

1. 어떤 시점으로 복구할지 결정합니다.
2. 복구 시 사라질 데이터 범위를 확인합니다.
3. 앱을 임시 점검 모드로 둘지 결정합니다.
4. 복구 후 smoke test를 수행합니다.

## 7. OWNER 계정 접근 불가 시 대응

직접 DB를 수정하지 말고 개발자에게 확인을 요청합니다. 마지막 OWNER 보호 로직이 있으므로 앱에서 모든 OWNER가 사라지는 상황은 방지되어야 합니다.

## 8. 초대 링크 분실 시 대응

raw token은 DB에 저장되지 않으므로 기존 링크를 다시 볼 수 없습니다. OWNER가 초대 재발급을 실행해 새 링크를 생성합니다.

## 9. 직원이 로그인하지 못할 때 확인할 것

- 전화번호가 올바른지
- 직원 상태가 ACTIVE인지
- 초대 가입이 완료되었는지
- 비밀번호를 잘못 입력하고 있는지

## 10. 휴가 잔여 일수가 이상할 때 확인할 것

- 입사일
- 기준 연도
- LeaveAdjustment
- PENDING/APPROVED 요청
- WITHDRAWN/REJECTED/CANCELLED 제외 여부
- 회사 휴일 등록 여부

## 11. AuditLog로 변경 이력 확인

OWNER는 `/admin/audit-logs`에서 주요 변경 이력을 확인합니다.

## 12. 직접 DB에서 수정하면 안 되는 항목

비개발자는 DB를 직접 수정하면 안 됩니다. 특히 다음 항목은 앱의 정합성과 보안을 깨뜨릴 수 있습니다.

- `passwordHash`
- `tokenHash`
- `Session`
- `Invitation.status`
- `LeaveRequest.status`
- `AuditLog`
- 마지막 OWNER role/status

직접 DB 수정이 필요한 경우 반드시 개발자 확인 후 백업을 먼저 수행합니다.
