# 2차 휴가 고도화 위험 검토

## 1. 1차 MVP 안정성 훼손 위험

위험:

- `LeaveType` enum, `LeavePolicy`, `LeaveRequest`를 급하게 변경하면 현재 동작하는 요청/승인 흐름이 깨질 수 있다.

대응:

- 2차 초반에는 adapter 계층을 둔다.
- 기존 1차 테스트를 회귀 테스트로 고정한다.
- migration 전에 데이터 모델 문서와 테스트 계획을 먼저 승인한다.

## 2. 휴가 잔여 계산 불일치 위험

위험:

- 기존 `LeaveAdjustment + LeaveRequest` 계산과 신규 `LeaveLedger` 계산이 다를 수 있다.

대응:

- dual-read 기간을 둔다.
- 기존 계산 결과와 ledger 계산 결과를 비교하는 검증 리포트를 만든다.
- 장부 이벤트 생성은 요청 상태 변경 transaction 안에서 처리한다.

## 3. migration 위험

위험:

- enum 기반 type을 DB 모델 기반 type으로 옮기는 과정에서 기존 요청의 type mapping이 깨질 수 있다.

대응:

- migration 전에 dry-run backfill script를 만든다.
- 기존 enum 5개를 신규 row로 명확히 매핑한다.
- rollback 계획을 문서화한다.

## 4. 연차 법무/노무 해석 위험

위험:

- 연차 부여, 소멸, 이월, 퇴사 정산은 법적 해석과 회사 취업규칙에 영향을 받는다.

대응:

- 시스템은 참고 계산으로 표현한다.
- 실제 운영 전 노무 전문가 검토를 필수로 둔다.
- 연차 촉진, 연차수당, 퇴사자 정산은 3차 이후로 분리한다.

## 5. 증명자료 개인정보 위험

위험:

- 진단서, 가족관계증명서, 예비군 통지서 등은 민감한 개인정보를 포함할 수 있다.

대응:

- 2차 초반에는 파일 스토리지 연동을 하지 않는다.
- attachmentUrl 또는 metadata만 제한적으로 관리한다.
- AuditLog에는 파일 내용, token, private URL을 저장하지 않는다.
- OWNER/승인자 외 접근을 제한한다.

## 6. 시간차/분차와 근무시간 정책 연결 위험

위험:

- 시간/분 단위 휴가는 근무시간, 휴게시간, 유연근무제와 연결되어야 정확하다.

대응:

- 2차에서는 `LeaveRequestSegment` 모델을 준비하되 시간/분차 사용은 제한적으로 연다.
- 근무시간 정책 모델은 별도 단계에서 설계한다.

## 7. 승인 정책 복잡도 증가 위험

위험:

- 순차 승인, 지정 승인자, 상위 조직장 승인까지 한 번에 넣으면 상태 모델이 복잡해진다.

대응:

- 2차에서는 기본 승인 정책 모델만 만들고 실제 복잡한 순차 승인은 후순위로 둔다.
- 기존 OWNER/LEAD 정책을 기본값으로 유지한다.

## 8. 테스트 범위 증가 위험

위험:

- 휴가 유형, 지급, 장부, segment, 증빙, 승인 정책이 동시에 추가되면 테스트 조합이 급격히 늘어난다.

대응:

- 단계별 feature flag 또는 관리자 설정으로 점진 노출한다.
- 각 단계마다 회귀 테스트를 먼저 통과시킨다.
- 계산 로직은 순수 함수 테스트를 우선 작성한다.

## 9. 단계적 배포 전략

권장 전략:

1. 문서와 테스트 계획 확정
2. 휴가 유형 모델 추가
3. 기존 enum과 신규 모델 dual-read
4. 맞춤휴가 생성/지급
5. LeaveLedger 도입
6. ledger와 기존 계산 비교
7. segment 도입
8. 증빙 metadata 도입
9. 연차 정책 고도화
10. 승인 정책 확장

각 단계는 production 데이터 백업 후 진행한다. 대규모 migration은 업무 시간이 아닌 시간에 적용하고, 적용 전후 smoke test를 수행한다.
