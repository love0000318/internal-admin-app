# flex형 휴가 기능 분석

## 1. 분석 목적

이 문서는 외부 HR 서비스의 휴가 관리 개념을 그대로 복제하지 않고, 우리 회사 내부 관리 앱의 2차 휴가 고도화 기준으로 재해석하기 위해 작성한다. 1차 MVP의 안정적인 휴가 요청/승인 흐름은 유지하고, 2차에서는 정책 기반 휴가 관리와 잔여 추적 가능성을 높이는 것을 목표로 한다.

이번 문서는 구현 지시서가 아니라 제품/아키텍처 기준 문서다. Prisma schema 변경, migration 생성, 기존 휴가 로직 변경은 이 문서 단계에서 수행하지 않는다.

## 2. 참고한 휴가 기능 개념

참고한 개념은 다음과 같다.

- 연차와 맞춤휴가를 분리한다.
- 맞춤휴가는 단순 이름 추가가 아니라 지급/사용/증빙/승인 정책을 가진다.
- 휴가 요청은 하루 단위뿐 아니라 반차, 시간 단위, 분 단위까지 확장 가능해야 한다.
- 잔여 휴가가 왜 특정 수량인지 장부처럼 추적할 수 있어야 한다.
- 휴가 유형별 승인 정책과 증명자료 정책을 분리할 수 있어야 한다.

외부 서비스의 화면, 문구, 브랜드, UI 구성은 복제하지 않는다. 기능 개념만 참고하고 우리 서비스의 권한, 데이터 모델, 운영 흐름에 맞게 재설계한다.

## 3. 연차와 맞춤휴가의 차이

### 연차

연차는 법정 유급휴가로 취급한다.

- 입사일 또는 회계연도 기준 부여가 필요하다.
- 월차, 연차, 장기근속 추가 부여, 소멸, 조정, 사용 내역 관리가 필요하다.
- 회사 취업규칙과 최신 근로기준법 검토가 필요하다.
- 시스템은 참고 계산을 제공하되 급여/노무 판단을 자동 확정하지 않는다.

### 맞춤휴가

맞춤휴가는 연차 외 회사가 자체적으로 운영하는 휴가다.

예시:

- 예비군
- 병가
- 경조사
- 리프레시
- 생일휴가
- 건강검진
- 포상휴가
- 대체휴무

맞춤휴가는 관리자가 생성, 수정, 비활성화할 수 있어야 하며, 직원에게 직접 지급할 수 있어야 한다.

## 4. 맞춤휴가 정책 항목

2차에서 검토할 맞춤휴가 정책 항목은 다음과 같다.

- 휴가명
- 설명
- 유급/무급 여부
- 유급 비율
- 부여 방식
- 부여 수량
- 부여 단위
- 사용 방식
- 사용 가능 단위
- 한 번에 모두 사용 여부
- 나눠서 사용 가능 여부
- 미사용 잔여 처리 방식
- 증명자료 필요 여부
- 증명자료 제출 시점
- 증명자료 안내문
- 휴일 포함 차감 여부
- 사용 가능 성별
- 제외 대상 조직
- 제외 대상 근로 유형
- 사용 만료 기한
- 공개 범위
- 승인 정책

1차 MVP의 `LeavePolicy`는 `LeaveType` enum 기반 정책이다. 2차에서는 enum 고정 구조에서 관리자가 생성 가능한 `LeaveType` 또는 `CustomLeaveType` 모델로 확장하는 방안을 검토한다.

## 5. 휴가 사용 단위

1차 MVP는 하루종일과 오전/오후 반차 중심이다. 2차 이후에는 다음 단위를 고려한다.

- 하루종일
- 오전 반차
- 오후 반차
- 시간 단위
- 분 단위

이를 위해 `LeaveRequestSegment` 구조를 검토한다.

예시:

- 5월 10일 하루종일
- 5월 11일 오전 반차
- 5월 12일 14:00~16:00 시간차
- 여러 날짜를 하나의 휴가 요청으로 묶되 날짜별 차감량을 다르게 처리

현재 `LeaveRequest`는 `startDate`, `endDate`, `halfDayPeriod`, `dayCount`만 가진다. 여러 날짜별 세부 차감량을 표현하기 어렵기 때문에, 2차에서는 `LeaveRequest`는 요청 header로 유지하고 실제 사용 단위는 segment로 분리하는 설계를 검토한다.

## 6. 증명자료 정책

휴가 유형별로 증명자료 정책이 필요하다.

정책 후보:

- 증명자료 불필요
- 요청 전 필수 제출
- 요청 후 제출 가능
- 선택 제출

증명자료 예시:

- 예비군 훈련 통지서
- 진단서
- 청첩장
- 가족관계증명서
- 건강검진 확인자료

2차 초반에는 실제 파일 스토리지를 붙이지 않는다. 우선 `attachmentUrl` 또는 `metadata` 기반으로 제출 상태와 안내문을 관리하고, 실제 스토리지 연동은 후순위로 둔다.

## 7. 휴가 조정과 휴가 장부

1차 MVP의 `LeaveAdjustment`는 직원별 휴가 수량을 수동 조정하는 단순 구조다. 2차에서는 `LeaveLedger` 개념을 도입해 잔여 수량이 변한 이유를 추적 가능하게 만든다.

LeaveLedger 이벤트 후보:

- `GRANTED`
- `USED`
- `PENDING`
- `PENDING_RELEASED`
- `EXPIRED`
- `ADJUSTED`
- `CANCELLED`
- `REJECTED`
- `WITHDRAWN`
- `CARRIED_OVER`

목표:

- 특정 직원의 잔여 휴가가 왜 17일인지 설명할 수 있다.
- 자동 부여, 수동 조정, 사용, 승인 대기, 취소, 소멸, 이월 이력이 장부처럼 남는다.
- 계산 로직의 source of truth를 분산시키지 않는다.

## 8. 연차 정책 고도화

연차 정책 후보:

- 입사일 기준 부여
- 회계연도 기준 부여
- 회계연도 시작일
- 월차 부여 방식
- 1년 미만자 부여 방식
- 1년 이상자 부여 방식
- 장기근속 추가 부여
- 최대 연차 한도
- 소멸 정책
- 유예기간
- 이월 가능 여부
- 퇴사자 정산 기준
- 연차 촉진

연차 촉진, 재직자/퇴직자 정산, 연차수당 계산은 3차 이후로 분리한다. 법무/노무 판단은 시스템이 최종 확정하지 않으며, 실제 운영 전 전문가 검토가 필요하다.

## 9. 승인 정책 확장

1차 MVP는 OWNER/LEAD 승인 구조다. 2차 이후 휴가 유형별 승인 정책을 확장할 수 있다.

승인 정책 후보:

- 승인 불필요
- 단일 승인
- 순차 승인
- OWNER 승인
- 팀 리드 승인
- 상위 조직장 승인
- 지정 승인자 승인

2차 문서화 단계에서는 순차 승인 구현까지 진행하지 않는다. 다만 `ApprovalPolicy` 모델 후보와 `LeavePolicy` 연결 구조를 설계한다.

## 10. 우리 서비스에 반영할 항목

2차에서 우선 반영할 항목:

- 연차와 맞춤휴가 개념 분리
- 관리자 생성형 맞춤휴가 유형
- 맞춤휴가 지급
- LeaveLedger 장부
- LeaveRequestSegment 설계
- 증명자료 metadata 정책
- 휴가 유형별 승인 정책 초안
- 휴가 사용 내역/히스토리 화면

## 11. 우리 서비스에 반영하지 않을 항목

1차 또는 2차 초반에 반영하지 않을 항목:

- 외부 서비스 UI/문구/브랜드 복제
- 실제 파일 업로드 스토리지 연동
- 실제 노무/급여 정산 자동화
- 연차 촉진 자동화
- 퇴사자 정산 자동화
- 복잡한 순차 승인 전체 구현
- 외부 캘린더/알림 연동

## 12. 2차에서 구현할 항목

- 휴가 유형 모델 정리
- 맞춤휴가 생성/수정/비활성화
- 맞춤휴가 직원 지급
- LeaveLedger 도입
- 휴가 요청 화면 개선
- LeaveRequestSegment 도입
- 증명자료 metadata 도입
- 휴가 사용 내역/히스토리 화면

## 13. 3차 이후로 미룰 항목

- 연차 촉진
- 퇴직자 정산
- 연차수당 계산
- 실제 파일 스토리지
- 외부 캘린더 연동
- 카카오톡/슬랙 알림
- 복잡한 순차 승인
- 관리자 통계 대시보드

## 14. 법무/노무 검토가 필요한 항목

- 입사일/회계연도 기준 연차 부여 정책
- 1년 미만자 월차 부여 정책
- 장기근속 추가 부여
- 최대 연차 한도
- 소멸 및 이월 정책
- 퇴사자 정산
- 연차 촉진
- 무급/유급 비율이 급여에 미치는 영향

## 15. 외부 서비스 복제 금지 원칙

외부 서비스는 기능 개념과 업무 흐름만 참고한다. UI 배치, 문구, 브랜드 표현, 화면 구성, 데이터 명칭을 그대로 복제하지 않는다. 우리 서비스의 1차 MVP 구조, 권한 모델, 데이터 정합성 원칙에 맞춰 재설계한다.
